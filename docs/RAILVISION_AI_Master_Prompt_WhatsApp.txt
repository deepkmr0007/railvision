4. CRITICAL FEATURE: NON-STOP STATION CROSSING
====================================================================

Allow the user to monitor a train between two stations even when the first/reference station is not a scheduled halt.

Example:
“Track train 12951 from Rewari to Delhi. Check every 15 minutes. Report when it passes Rewari even if it does not stop there, and continue until Delhi.”

Support three distinct event classes:

1. SCHEDULED HALT
   The train is scheduled to stop. Show scheduled and actual times where available.

2. CONFIRMED PASSAGE
   The train passes a station without a scheduled halt and a trustworthy source supplies sufficiently granular position or passage evidence. Store source, event timestamp, received timestamp and method.

3. ESTIMATED CROSSING
   No confirmed crossing evidence is available. Estimate only when route sequence, latest verified observation and defensible travel-time assumptions support it. Label as ESTIMATED and provide a range/uncertainty when appropriate.

Never infer physical crossing merely because a scheduled time has passed. If evidence is insufficient, report “Crossing not verified” and continue monitoring.

Store:
- Train and service date.
- Station code/name.
- Event class.
- Scheduled time if relevant.
- Confirmed passage timestamp or estimated time/range.
- Data source and source timestamp.
- Confidence/verification status.
- Calculation method/version.
- Audit history of corrections.

Handle route diversions, reversed train direction, midnight, cancelled trains, stale updates, skipped stops, duplicate observations and out-of-order events.

5. CHATBOT AND TRACKING TASKS
====================================================================

Build an English/Hindi/Hinglish conversational assistant. It must use backend tools and structured results rather than model memory for live facts.

Example commands:
- “Where is train 12951 now?”
- “Has it crossed Rewari?”
- “Does this train stop at Rewari?”
- “Estimate when it will cross this station.”
- “Track this train every 15 minutes until Delhi.”
- “Alert me if the delay exceeds 30 minutes.”
- “Show chart vacancy from my boarding station.”
- “Pause this tracking.”
- “Change the interval to 30 minutes.”
- “Stop updates for this train.”

The bot should resolve train/station/date ambiguity and ask a short follow-up when a required value is missing. Before enabling a persistent task, summarize the train, service date, reference station, endpoint, interval, data availability and delivery destination; require confirmation when needed.

Tracking tasks must persist on the server when the app is closed, subject to service availability and source limitations. Support create, pause, resume, update, cancel and delete. Apply provider rate limits, shared polling, caching, exponential backoff and notification deduplication. Do not create an independent upstream poll for every user when one shared observation can serve multiple subscribers.

6. WHATSAPP DELIVERY: PERSONAL, GROUPS, CHANNELS
====================================================================

Create a modular WhatsApp delivery adapter. Research the current official Meta WhatsApp Business Platform/Cloud API documentation and the current capabilities and eligibility rules for one-to-one messages, groups, and channels. Do not assume the same API supports all three.

A. PERSONAL / ONE-TO-ONE MESSAGES
- Support opt-in users through the official WhatsApp Business Platform/Cloud API or a properly authorized provider.
- Implement inbound webhook verification and message processing.
- Allow users to start a chat, link their account to RAILVISION, create a tracking task, set an interval, choose a destination and stop notifications.
- Respect consent, opt-out, approved message templates where required, business messaging rules, session windows, rate limits and applicable charges.
- Provide a `/help` equivalent and simple natural-language commands.
- Never send unsolicited messages to scraped or purchased phone lists.

B. WHATSAPP GROUPS
- Research official group-messaging API availability and eligibility at implementation time. Some group capabilities may be restricted to qualifying business accounts, group sizes, or approved access.
- If the official API is available and the project qualifies, implement it using official documented endpoints.
- If the project is not eligible, do not pretend ordinary Cloud API can freely post into any existing WhatsApp group.
- Offer practical compliant alternatives: opt-in individual recipients, a Telegram group bot, email, in-app notifications, or an admin-operated channel workflow.
- Do not use unofficial WhatsApp Web automation, session-cookie extraction, QR-session hijacking, or brittle libraries that impersonate a user client for production.
- Group messages should be concise, configurable, rate-limited, and only sent to groups where the integration is authorized.

C. WHATSAPP CHANNELS
- Research whether an official, supported API exists for programmatically publishing Channel updates and whether this account/project is eligible.
- If no supported API is available, provide a safe fallback: generate copy-ready update text for a channel admin to publish manually, or use an approved third-party service only after validating its legitimacy and permissions.
- Do not promise automatic channel publishing without a verified supported integration.
- Channels are primarily broadcast-style; design two-way commands through a personal chat or web dashboard instead.

D. DELIVERY DESTINATIONS
Let each tracking task choose one or more supported destinations:
- RAILVISION app.
- Browser notifications.
- Android push.
- Email.
- WhatsApp personal chat, when authorized.
- WhatsApp group, only if supported and approved.
- WhatsApp Channel, only if an official/authorized publishing route is verified.
- Telegram bot/group as an optional practical group-broadcast alternative.

E. MESSAGE TYPES
- Periodic running-status report.
- Confirmed non-stop passage.
- Estimated crossing, clearly labelled.
- Delay threshold alert.
- Cancellation/diversion.
- Chart vacancy change only if the authorized source supports monitoring.
- Data stale/source unavailable warning.
- Tracking completed.

9. SECURITY AND PRIVACY
====================================================================

- HTTPS/TLS for all network traffic.
- Secrets in environment-specific secret storage, never committed to source control.
- Verify Meta webhook signatures and challenge tokens correctly.
- Authenticate and authorize user tracking tasks.
- Prevent one user from accessing another user's task or phone details.
- Rate-limit chatbot and webhook endpoints.
- Protect against injection, replay attacks, spoofed callbacks and abuse.
- Minimize retention of phone numbers and message bodies.
- Record consent and support unsubscribe/delete requests.
- Never log access tokens, API secrets or unnecessary passenger data.
- Never request IRCTC passwords or store booking credentials in plaintext.
- Use least privilege, dependency scanning, audit logs and backup/restore tests.
- Ask for approval before paid API use, sending campaigns, or production deployment.
